# Phase 9 Owned-Demand Publication Proof Ledger

Date: 2026-08-21
Status: stacked release candidate; Production database and application unchanged
Canonical campaign: `amm_owned_demand_2026`

## Executive decision

Reuse the protected `/admin/distribution` command, canonical Neon database,
existing Lead Center authentication, exact UTM builder, seller/buyer/renter
funnels, and retained approved visuals. Add one narrowly scoped append-only
ledger for evidence observed after an authorized person uses a native channel.

This closes the gap between three different facts that must not be conflated:

1. a compliant draft and tracked URL were prepared;
2. an authorized operator observed a native-platform state; and
3. a consumer later arrived with matching first-party attribution.

The ledger proves only item 2. It is not provider verification, reach,
engagement, a lead, a qualified opportunity, or a conversion.

## Evidence-backed reason for the work

A read-only aggregate query against canonical Neon Production at
`2026-08-21T16:49:56.789167Z` found six test leads, six suppressed leads, zero
live leads, zero contactable live leads, zero first-response samples, zero live
notification failures, zero outcomes, zero spend rows, zero active experiments,
and zero overdue routing rows. No consumer identity or contact detail was read
or retained in the evidence.

The immediate constraint is measurable owned-demand activation. Another score,
AI summary, or economics dashboard would have no live demand to optimize.

- Internal command: authenticated `/admin/distribution`.
- Attribution: canonical source, medium, campaign, and `utm_content` generated by
  the existing UTM builder.
- Database: Neon project `bitter-star-20214385`, Production branch
  `br-round-base-auh6h2wd`, database `neondb`.
- Authentication: existing Lead Center session and server-side RBAC.
- Audit: existing immutable `audit_logs` table.

No parallel CRM, publisher, campaign database, Supabase runtime, browser token,
or provider credential was added.

## Native-platform mechanism refresh

- [Google Business Profile posts](https://support.google.com/business/answer/7342169?hl=en)
  support Update, Offer, and Event posts and expose native states such as live,
  pending, or not approved. The ledger records the observed state; it does not
  bypass Google's review or claim approval.
- [Google Analytics campaign URL guidance](https://support.google.com/analytics/answer/10917952?hl=en-uk)
  and [manual campaign dimensions](https://support.google.com/analytics/answer/11242870?hl=en)
  support consistent source, medium, campaign, and content parameters. Every
  proof resolves those values from code rather than accepting typed UTMs.
- [Facebook Page publishing](https://www.facebook.com/help/www/181155025579876?locale=en_GB),
  [Page post attribution](https://www.facebook.com/help/225783087608655/), and
  [post insights](https://www.facebook.com/help/131809553587433) keep identity,
  publication, and performance in the native Page/Meta surfaces. This release
  stores a minimized URL or reference only; it does not call Meta.
- [LinkedIn Page posting](https://www.linkedin.com/help/linkedin/answer/a563045)
  and [Page analytics](https://www.linkedin.com/help/linkedin/answer/a1674944?lang=en-US)
  likewise remain native operator actions. A proof record does not choose a Page
  identity or publish a post.

These sources describe current mechanisms. They are not authorization to post
and do not support a performance promise.

## Architecture and trust boundaries

```text
Existing command + canonical tracked placement
  -> authorized person reviews and acts in native platform
  -> administrator or primary lead owner records observed evidence
  -> Server Action rechecks growth:manage
  -> runtime validation + channel/host/state/proof allowlists
  -> raw final copy normalized and SHA-256 hashed in memory
  -> Preview mutation guard
  -> parameterized Neon RPC
  -> append-only proof row + immutable audit event in one transaction

Later consumer submission
  -> canonical lead capture
  -> exact first/last-touch attribution
  -> Growth ledger comparison (separate from publication proof)
```

The recording path makes no external HTTP request. It cannot publish, schedule,
send email or SMS, target an audience, create an ad, change spend, or mutate a
lead.

## Data minimization and validation

Stored fields are limited to:

- random proof ID and deterministic idempotency hash;
- channel and placement keys;
- observed state and proof type;
- canonical campaign/source/medium/content and tracked AskMagicMike.com URL;
- either an allowlisted public native-platform URL or a non-sensitive evidence
  reference;
- SHA-256 of the exact final copy, never the raw copy;
- optional internal creative asset key;
- approval reference, observation time, recorder identity, test flag, and
  minimized control metadata.

Validation rejects:

- non-HTTPS or unapproved public evidence hosts;
- embedded URL credentials, secret-like query parameters, emails, phone
  numbers, and credential patterns;
- state/proof combinations that do not match the channel mechanism;
- unresolved placeholders, unsupported guarantees/valuation claims, and known
  Fair Housing risk phrases;
- raw copy under 20 or over 5,000 characters; and
- unknown channels, placements, or campaign attribution.

Persisted URLs are allowlisted again on read before React receives an `href`.
React renders all references as escaped text. External links use
`noopener noreferrer`.

## Authorization and runtime controls

- `report:view` can inspect the command and proof history.
- New `growth:manage` permission is limited to `administrator` and
  `primary_lead_owner`.
- The Server Action rechecks `growth:manage`; UI hiding is not authorization.
- Next.js Server Action Origin/Host protections remain enabled.
- Preview is read-only unless the existing explicit Preview database mutation
  controls are all enabled; default behavior is fail-closed.
- The page is force-dynamic and uncached.
- SQL is parameterized. No secret, raw copy, provider payload, or environment
  dump is logged.

## Database contract

Migration `20260821170000_owned_demand_publication_proofs.sql` is additive and
creates:

- one server-only RLS-enabled table;
- canonical channel/UTM/state/proof/evidence constraints;
- bounded indexes;
- an UPDATE/DELETE rejection trigger; and
- `record_owned_demand_publication_proof_v1`, an idempotent `SECURITY INVOKER`
  function that inserts one proof and one `growth.publication_proof_recorded`
  audit event atomically.

Public, `anon`, and `authenticated` access is denied. The existing server role
receives only the table and function privileges needed by this path.

## Operator workflow

1. Open the protected Distribution Command.
2. Select the exact channel and placement already used.
3. Choose the state actually visible in the native platform.
4. Choose the matching proof type.
5. Enter either the public native URL or a non-sensitive internal reference.
6. Paste the exact final copy used. It is validated, hashed, and discarded.
7. Enter the existing owner/broker approval reference without personal contact
   information or credentials.
8. Confirm that the external action already occurred and submit the evidence.
9. Verify the resulting status, immutable history, and matching UTM placement.

If the native platform later removes or rejects the placement, append a removed
or not-approved observation. Do not edit history.

## Production cutover

Offline plan:

```text
pnpm run phase9:publication-proof:cutover -- --plan
```

After exact approval, the guarded runner requires an unpooled owner connection
through the secure environment only. It performs read-only preflight, pins the
migration SHA-256, validates the canonical Neon identity and prerequisite PR
181 schema, acquires an advisory lock, creates a mode-600 validated backup,
applies one transaction, inserts the migration ledger row, and checks object,
RLS, trigger, constraint, privilege, audit, lead-state, and zero-seed-row
postconditions.

Exact gate:

```text
APPROVE PHASE 9 OWNED-DEMAND PUBLICATION PROOF LEDGER PRODUCTION MIGRATION, MERGE, AND PRODUCTION DEPLOYMENT
```

This gate does not authorize a social/GBP/email/print publication. Each external
placement still requires the final identity, copy, visual, URL, and removal path
to be approved.

## Rollback

- Before merge: close or leave the stacked PR unmerged.
- Application: promote the immediately preceding verified Vercel Production
  deployment; the additive table may remain dormant.
- Database: prefer a forward fix. Do not delete proof or audit history. Preserve
  the validated backup until authenticated application verification passes.
- Native channel: remove or correct only the exact externally approved
  placement in its native account, then append a removal proof. Application
  rollback cannot remove an external post.

## Truthful limitations

- No public post, email signature, QR placement, lead, message, spend, or
  provider event is created by this feature.
- A proof is operator-attested evidence, not cryptographic provider attestation.
- Zero live leads means there is no conversion-lift claim or valid channel
  ranking yet.
- Final broker/BIC/legal review remains a human decision.
